Why Dropbox left S3

Dropbox ran its web and metadata services in its own datacenters but kept user file content in Amazon S3. By 2016 it reported more than 500 million signups and 500 PB of user data, up from about 40 PB in 2012, and said that controlling the storage stack could improve both performance and unit economics [B1].

Magic Pocket became a major project in 2013, dark-launched in August 2014 and served more than 90% of user data by October 2015 [B1]. A large AWS storage commitment that was due to expire set a hard date [T4][T5]. Dropbox's engineers called cost the leading reason at Dropbox's scale, and said third-party infrastructure stays the right choice where its economics or reach fit a workload [T6]. Dropbox kept a hybrid setup: AWS kept the remaining user data and served regional needs [F1, p. 120][T5][T8].

Architecture

Magic Pocket is an immutable block store. Files are split into blocks of up to 4 MB, and a block never changes once written. Blocks are replicated when written and erasure coded later, and each one is stored in more than one zone [B2][B5]. Satchel keeps those ideas at laptop scale, one cell over three zones (DDL-005):

Writing a file

  1. The files service splits the file into blocks of up to 4 MiB and hashes each one with SHA-256 (DDL-001).
  2. For each block, the frontend asks the Block Index whether it already has that hash. If so, the block is not stored again: that's dedup (DDL-002).
  3. Otherwise the frontend picks an open volume and appends the block to all three of its replicas, one per zone. Each node fsyncs before replying, and all three must return the same offset (DDL-006, DDL-018).
  4. Only then is the block recorded in the index. If any replica fails, the frontend tries another open volume, the "write to all, no quorum, retry elsewhere" rule Dropbox describes [B2].
  5. The files service records the file's ordered block list (DDL-020).

Replication, then erasure coding

New data is replicated: three full copies, 3x the bytes. When a volume fills (64 MiB) or has been open 10 minutes, the Master closes it and encodes it as Reed-Solomon RS(6,3): 6 data fragments and 3 parity fragments, three per zone, so 1.5x the bytes and any 3 of the 9 can be lost (DDL-004, DDL-007, DDL-008). Magic Pocket also replicates new blocks first and erasure codes them later [B2][B5].

The local install keeps volumes replicated, since RS(6,3) needs 9 nodes and it runs 3. The cost panel shows both figures.

When a node fails

Reads try another replica straight away. Writes move to another open volume. If a node stays down longer than the repair threshold (15 minutes in Magic Pocket [B2], 30 seconds in Satchel's tests), the verifier rebuilds its replicas or fragments on healthy nodes (DDL-010). The Disk Scrubber keeps reading data back to catch silent corruption (DDL-012) [B3].

Files on top of blocks

Magic Pocket stores only blocks; Dropbox keeps file metadata in separate systems such as FileJournal [B2]. Satchel adds a small SQLite manifest so the demo can store whole files: each file's block list, plus a reference count per block, so deleting a file only releases blocks no other file uses. That layer is a deliberate deviation from Magic Pocket (DDL-020).

Rent or own

Renting costs per GB-month and per request, from the first byte. Owning costs a lot up front and every month, whatever you store: servers, power, space and the engineers who run it. So the cloud wins small and owning wins big (our inference, which the cost model tests). The calculator runs the same cost engine as the report and finds the break-even size for any inputs. The live panel on the store page shows the marginal side: what your files add to each bill.

The on-prem figure on the store page is hardware paid off over its life, drive power and colocation for the raw bytes only. Staff, switches and transit are fixed costs that show up only at scale, so they're in the calculator, not in the per-file figure (our inference).

Run it yourself

That installs the latest release into ~/satchel and starts the index, three storage nodes (one per simulated zone), the frontend, the verifier with the Master, and the files API on 127.0.0.1:47800. ~/satchel/bin/satchel stop, status, logs and uninstall do what they say.
